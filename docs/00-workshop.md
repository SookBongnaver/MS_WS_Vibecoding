# 바이브코딩 준비하고 시작하기

[처음으로](../README.md)

**목표는 정해진 앱을 복제하는 것이 아니라, 내가 원하는 것을 자연어로 만들고 개선하는 방법을 익히는 것입니다.**

이 장은 모든 참가자의 공통 시작 가이드입니다. Foundry·DB 구성은 필수 사전 준비가 아닙니다. 필요한 기능이 생기면 코딩 도우미와 상의하고 승인된 방법으로 추가합니다.

## Step 1. 준비물 확인

| 준비물 | 확인할 것 |
|---|---|
| 노트북·충전기·인터넷 | 실습 중 접속과 전원 유지 |
| 코딩 도구 하나 | Codex CLI, GitHub Copilot, Claude Code 중 선택 |
| 로그인·사용 권한 | 단순 계정 보유가 아니라 해당 코딩 기능 사용 가능 여부 |
| 파일·폴더를 확인할 편집기 | 이 가이드는 VS Code를 예시로 사용 |
| 설치·실행 가능한 PC | 회사 정책상 제한되면 운영자에게 사전 문의 |
| 만들고 싶은 아이디어 | 없으면 저장소의 사업 관련 주제 5개 중 선택 |
| 연습용 자료 | 합성 데이터·가상 문구. 실제 고객정보는 사용하지 않음 |

**아직 준비하지 않아도 되는 것:** 모든 개발 언어, Azure 리소스, SQL·Cosmos DB, 실행용 AI 모델, 배포 서버. 선택한 코딩 도구의 설치에 필요한 항목만 먼저 준비합니다.

## Step 2. 도구 하나를 설치하고 로그인

[도구별 설치 안내](04-models-and-tools.md)를 열어 선택한 도구의 경로만 따라갑니다.

| 도구 | 시작 위치 |
|---|---|
| GitHub Copilot | VS Code에서 폴더를 열고 Chat의 Agent 모드 |
| Codex CLI | 작업 폴더의 터미널에서 `codex` |
| Claude Code | 작업 폴더의 터미널에서 `claude` |

로그인 후 아래를 입력합니다. 아직 파일은 만들지 않습니다.

```text
나는 개발 경험이 없는 워크숍 참가자야.
현재 작업 폴더와 파일을 읽거나 수정할 수 있는지 확인해줘.
아직 파일 생성·수정, 프로그램 설치, 명령 실행은 하지 마.
내가 요청하면 어떤 순서로 작업을 진행하는지 간단히 설명해줘.
```

**확인:** 도우미가 응답하고 현재 프로젝트 접근 범위를 설명합니다. 제품 버전에 따라 버튼·메뉴가 다를 수 있습니다. 실행 권한을 전부 허용하는 모드로 바꾸지 않습니다.

## Step 3. 새 작업 폴더 열기

1. Windows 파일 탐색기에서 문서 폴더를 엽니다.
2. `MyVibeProject`처럼 새 폴더를 만듭니다. 기존 업무 파일 폴더를 쓰지 않습니다.
3. VS Code에서 **File → Open Folder**로 새 폴더를 엽니다.
4. CLI를 선택했다면 **Terminal → New Terminal**을 열고 선택 도구를 실행합니다.
5. Chat 방식이라면 이 폴더를 연 VS Code의 Agent 대화창을 사용합니다.

이 GitHub 저장소는 옆에서 읽는 교재입니다. 처음부터 복잡한 예제 코드를 복제하지 않아도 됩니다. 선택 예제를 이용하고 싶을 때만 해당 시작 코드를 내려받습니다.

**확인:** 탐색기에 새 프로젝트 폴더가 보이고, 코딩 도우미가 같은 폴더에서 작업합니다.

## Step 4. 만들고 싶은 것을 설명

[아이디어 5개](../README.md) 중 고르거나 본인 업무에서 출발합니다. 아래 대괄호를 직접 바꿔 입력하세요.

```text
나는 [사용할 사람]을 위한 [만들고 싶은 것]을 만들고 싶어.
지금은 [불편한 점]이 있어.
사용자가 [입력할 내용]을 주면 [원하는 결과]가 나오면 좋겠어.

아직 코드를 만들지 말고 나와 요구사항부터 정리해줘.
모호한 부분은 쉬운 말로 한 번에 질문 하나씩 해줘.
처음에 만들 작은 기능 하나와 나중에 추가할 기능을 구분해줘.
특정 제품이나 DB가 꼭 필요하다고 가정하지 마.
```

예: “마케팅 담당자가 가상 광고 실적을 입력하면 채널별 성과를 비교하는 도구를 만들고 싶어.”

**확인:** 누구를 위한 것인지, 첫 기능이 무엇인지, 어떤 결과를 기대하는지 설명할 수 있습니다. 화면 모양부터 정해도 좋지만 실제로 어떤 일을 할지도 정합니다.

## Step 5. 가장 작은 버전 제작 요청

```text
지금 정리한 첫 기능만 작동하는 버전을 만들어줘.
내 PC에서 가장 단순하게 실행할 수 있는 방법을 먼저 제안해줘.
실제 회사 데이터 대신 작은 가상 자료를 사용해.

무슨 파일을 만들고 어떤 프로그램이 필요한지 먼저 설명해줘.
설치나 외부 서비스 연결이 필요하면 이유와 대안을 말하고 확인을 받아줘.
새 유료 리소스를 만들거나 외부로 데이터를 보내지 마.
완료하면 내가 누르거나 입력할 실행 방법을 순서대로 알려줘.
```

**확인:** 계획이 아이디어와 맞으면 구현을 요청합니다. 도우미가 제안한 파일 변경과 명령은 읽고 승인합니다. 모든 앱이 동일한 언어·실행 명령을 쓰는 것은 아닙니다.

## Step 6. 내가 직접 실행

1. 변경된 파일이 새 프로젝트 폴더 안에 있는지 확인합니다.
2. 도우미가 안내한 실행 명령 또는 파일 열기 방법을 따릅니다.
3. 안내가 불분명하면 아래처럼 요청합니다.

```text
지금 만든 것을 내가 직접 실행하려고 해.
어느 폴더에서, 어느 터미널에, 무엇을 입력해야 하는지 한 단계씩 알려줘.
브라우저를 열어야 한다면 정확한 로컬 주소를 알려줘.
실행 성공을 무엇으로 확인하면 되는지도 설명해줘.
```

4. 샘플 값을 입력하고 기대한 결과와 비교합니다.

**확인:** “만들었습니다”라는 답변이 아니라 실제로 열린 화면, 생성 파일, 계산 결과 또는 프로그램 응답이 있습니다. 에이전트를 만들었다면 모델과 도구가 실제 연결됐는지, 아직 모의 응답인지를 구분합니다.

## Step 7. 오류와 불편한 점을 설명해서 수정

```text
내가 한 행동: [버튼을 눌렀거나 실행한 명령]
기대했던 결과: [원하는 동작]
실제로 나온 결과: [관찰한 현상]
오류 메시지: [비밀 값과 개인정보를 제거한 메시지]

문제 원인을 설명하고 수정해줘.
기존에 잘 되던 기능은 유지해줘.
수정 후 내가 같은 상황을 다시 확인할 방법을 알려줘.
```

오류가 없어도 “글씨가 작다”, “결과의 이유를 모르겠다”, “조건을 바꾸면 다시 계산해줬으면 좋겠다”처럼 말하면 됩니다. 한 번에 기능 하나씩 바꾸고 직접 재실행합니다.

## Step 8. 필요한 기능을 추가

기술 이름부터 고를 필요는 없습니다. 필요한 동작을 말하세요.

| 내가 하고 싶은 말 | 그때 검토할 것 |
|---|---|
| “다시 열어도 내용을 기억해줘” | 로컬 파일·브라우저 저장·DB 중 적합한 방식 |
| “여러 사람이 같은 데이터를 쓰게 해줘” | 공유 저장소·DB·사용자 권한 |
| “질문을 이해해서 필요한 작업을 골라 처리해줘” | 실행 모델·도구 호출·에이전트 구조 |
| “사내 자료에서 근거를 찾아줘” | 승인된 자료 연결·검색·접근 권한 |
| “동료도 접속해서 써보게 해줘” | 승인된 공유·호스팅·인증 방식 |
| “결과를 비교하기 쉽게 보여줘” | 표·차트·웹 화면 |

추가 요청:

```text
이제 [필요한 기능]을 추가하고 싶어.
현재 구조에서 가장 간단한 방법과 나중에 확장할 방법을 설명해줘.
외부 서비스가 필요하면 왜 필요한지, 비용·계정·권한이 무엇인지 알려줘.
이미 사용할 수 있는 환경이 있는지 먼저 물어보고,
새 리소스 생성·외부 전송·유료 호출은 내 확인 전에는 하지 마.
```

예를 들어 Azure 모델과 SQL이 적합하다고 결정했을 때 [선택 구성 가이드](01-environment.md)를 활용합니다. **모든 참가자가 이 경로를 거쳐야 하는 것은 아닙니다.** 현재 저장소의 Python 예제는 Azure 전용이며, 다른 연결 방식을 자동 지원하는 것은 아닙니다.

## Step 9. 동료와 논의

동료에게 설명 없이 사용해보게 하고 “어디가 막혔는지”, “무엇이 더 필요했는지”를 듣습니다. 그 피드백을 다시 코딩 도우미에 전달해 개선합니다.

[논의·개선·결과 공유](03-improve-and-share.md)로 이어갑니다.
